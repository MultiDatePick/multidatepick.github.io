App-Seiten, Startseiten & Experience Cloud-Sites

MultiDatePick funktioniert auf jeder Lightning-Oberfläche, nicht nur auf Datensatzseiten. Der Trick ist eine einzige Eigenschaft: Static Parent Record Id.

Einrichtung ansehen Fehlerbehebung

Warum diese Seiten anders sind

MultiDatePick speichert die gewählten Termine als Datensätze auf einem verknüpften Objekt, jeden mit Verweis auf einen übergeordneten Datensatz. Die Komponente muss nur wissen, welchen.

  • Auf einer Datensatzseite (z. B. einem Event-Datensatz) übergibt Salesforce der Komponente automatisch die Id des aktuellen Datensatzes (die recordId). Sie müssen nichts weiter konfigurieren.
  • Auf einer App-Seite, Startseite oder Experience Cloud-Site gibt es keinen „aktuellen Datensatz“. Salesforce übergibt nichts. Ohne übergeordneten Datensatz weiß die Komponente nicht, wohin sie speichern soll, und blendet die Schaltfläche Speichern bewusst aus, statt eine anzuzeigen, die beim Klick scheitert.
Die Lösung ist die Eigenschaft Static Parent Record Id. Fügen Sie die Id eines bestimmten übergeordneten Datensatzes ein, und die Komponente verhält sich genau so, als stünde sie auf der Seite dieses Datensatzes. Es ist eine Eigenschaft, die Sie im Builder setzen. Mit einer statischen Ressource (Static Resource) in Salesforce, einer eigenen Funktion für hochgeladene Dateien, hat sie nichts zu tun.

Sie finden Static Parent Record Id im Eigenschaftenbereich, nachdem Sie MultiDatePick im Lightning App Builder auf eine App-Seite oder Startseite oder im Experience Builder auf eine Seite gezogen haben.

Static Parent Record Id oder Flow: Was wann passt

Static Parent Record Id richtet die Komponente auf einen festen übergeordneten Datensatz aus, also sieht jeder Besucher denselben Datensatz. Für manche Fälle ist das perfekt, für andere falsch. Wenn der Datensatz je Benutzer oder Besuch wechseln soll, steuern Sie ihn stattdessen über einen Bildschirm-Flow (Screen Flow). Ziehen Sie die Komponente auf einen Flow-Bildschirm und binden Sie ihre Parent Record Id an eine Variable, die der Flow zur Laufzeit ermittelt.

Static Parent Record Id, wenn der Datensatz für alle derselbe ist

  • Eine öffentliche Buchungsseite: eine Seite für Gäste zum „Termin anfragen“, auf der jede Buchung am selben übergeordneten Datensatz hängt (ein Büro, ein Standort oder eine Ressource). Eine feste Id ist genau richtig.
  • Ein Kalender für die ganze Org: ein einzelner Datensatz „Betriebsschließungen“ oder eine gemeinsame Ressource, die alle buchen und die sich nie je Benutzer ändert.
  • Ein fester Dashboard-Anker auf einer App- oder Startseite, der immer auf denselben Hauptdatensatz zeigt.

Faustregel: Nehmen Sie Static Parent Record Id, wenn die Antwort auf „Wessen Datensatz ist das?“ lautet: „Für alle derselbe.“

Ein Flow, wenn der Datensatz zur Laufzeit gewählt wird

  • Datensätze pro Benutzer: Jede Person sieht nur ihre eigenen (zum Beispiel landet jeder Auftragnehmer in seinem eigenen Urlaubskalender). Der Flow macht ein Get Records, bei dem der Inhaber oder ein verknüpfter Kontakt = {!$User.Id} ist, speichert die Id und gibt sie an die Komponente weiter.
  • Per URL gesteuert: Eine Eingabevariable des Flows liest ?id=… aus dem Link, sodass eine Seite viele Datensätze bedient. Das funktioniert auch für Gäste, ohne Anmeldung.
  • Erst auswählen: Auf Bildschirm 1 sucht oder wählt der Benutzer (einen Mitarbeitenden, einen Raum, einen Kunden); Bildschirm 2 zeigt den Kalender dieses Datensatzes.
Gast-Sites: Auf einer öffentlichen Site ohne Anmeldung ist der „Benutzer“ ein einziger gemeinsamer Gast, eine Auflösung pro Benutzer ($User) greift also nicht. Teilen Sie entweder einen Datensatz über Static Parent Record Id, oder steuern Sie ihn über einen URL-Parameter in einem Flow. Echte Kalender pro Benutzer brauchen angemeldete Benutzer.

Öffentliche Gast-Sites: die Checkliste in fünf Schritten

Auf einer öffentlichen Experience Cloud-Seite kann jeder ohne Anmeldung buchen. Erledigen Sie alle fünf Schritte, bevor Sie als Gast testen. Die Schritte 4 und 5 werden am häufigsten vergessen. Sehen Sie es in der Live-Demo, einer öffentlichen Gast-Site, in Aktion.

#SchrittWas Sie einstellen
1ObjektberechtigungenGeben Sie dem Gastbenutzer der Site Lesen, und Erstellen, wenn Gäste etwas absenden, auf jedes Objekt, das die Komponente nutzt. Gäste können nie bearbeiten oder löschen. Das ist eine Regel der Salesforce-Gastlizenz für jede App, behalten Sie Bearbeiten und Stornieren also Seiten hinter einer Anmeldung vor.
2Sicherheit auf FeldebeneLesen auf jedes Feld, das der Kalender anzeigt. Bearbeiten auf jedes Feld, das er schreibt, einschließlich Status-, Zeit- und Beziehungsfeldern. Denken Sie auch an die Felder für Geschäftszeiten und Schließtage der Ressource.
3Freigaberegel für GästeEine Freigaberegel mit Lesezugriff für den Gastbenutzer, damit Gäste die Datensätze sehen. Die externe organisationsweite Standardeinstellung des Objekts muss Privat sein, damit die Regel greift. Eine als Metadaten bereitgestellte Regel braucht unter Freigabeeinstellungen einen Klick auf Neu berechnen.
4Berechtigungssatz für GästeWeisen Sie MultiDatePick - Guest dem Gastbenutzer der Site zu. Er enthält den Zugriff auf die Apex-Klassen, über die der Kalender seine Daten lädt, plus die Lese- und Erstellrechte, die ein Gast auf den MultiDatePick-Objekten haben darf.
5Veröffentlichen und aktivierenVeröffentlichen und Aktivieren sind getrennte Schritte. Gäste sehen nur eine aktivierte Site.

Zwei Org-Einstellungen, die Gäste außerdem brauchen

EinstellungWarum
Standardinhaber für DatensätzeGäste können keine Datensätze besitzen, deshalb weist Salesforce jede Gastbuchung einem Standardinhaber zu. Sie legen ihn in den Experience-Arbeitsbereichen unter Verwaltung, Voreinstellungen fest.
Lesezugriff auf referenzierte DatensätzeEine Buchung, die auf eine Ressource oder einen übergeordneten Datensatz verweist, braucht Gast-Lesezugriff auf diesen Datensatz, sonst scheitert das Speichern mit einem Cross-Reference-Fehler. Verwenden Sie ein benutzerdefiniertes Objekt für alles, worauf Gäste buchen: Der Gastzugriff auf Kontakte und Accounts ist stark eingeschränkt.

Fehlerbehebung

SymptomLösung
Speichern erscheint nieEine der vier ist leer. Abseits einer Datensatzseite ist es meist Static Parent Record Id.
Kalender lädt, Speichern schlägt fehlKein Objektzugriff. Weisen Sie den Berechtigungssatz MultiDatePick - User zu; auf einer Site geben Sie dem Mitglieder- oder Gastprofil Lesen und Erstellen.
„Field does not exist“ beim SpeichernTippfehler im API-Namen. Kopieren Sie ihn aus Setup, Objekt-Manager. Ein Namespace-Präfix gehört nur zu Objekten eines anderen Pakets (z. B. acme__Visit_Date__c).
Site-Mitglieder sehen ihre Datensätze nichtLegen Sie eine Freigaberegel auf dem untergeordneten Objekt an (oder lockern Sie die organisationsweiten Standardeinstellungen).
Gespeicherte Termine verschwinden beim NeuladenLassen Sie Load Existing Dates (Vorhandene Daten vorladen) eingeschaltet (standardmäßig an).
Static Parent Record Id „isn't valid“Verwenden Sie eine echte 15- oder 18-stellige Id des übergeordneten Objekts, also des Objekts, auf das das Beziehungsfeld zeigt.
