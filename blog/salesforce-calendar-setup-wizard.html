Configuring a Salesforce Calendar Without Writing Code

100+ properties sounds like a project. It is a wizard of four steps that fills in the likely choices for you, with a live preview before you save anything.

Published August 19, 2026 · Updated October 31, 2026 · MultiDatePick

Most Salesforce components with real depth make you learn them twice: once to understand the properties, once to remember which combination you picked last time. The Setup Wizard exists so you do neither. It asks where the calendar goes and what each pick should save, fills in the fields it can work out, writes the configuration as metadata, and hands you a name you can use anywhere.

One way in, plus two shortcuts

The Create New tab opens on the guided setup. Two more tabs sit beside it for configs you already have.

Where the calendar goes, what each pick saves, then the likely fields filled in. Best for most setups.

Four steps, start to finish

StepWhat you set
1. Where it livesA record page of any object, an app or Home page, a Screen Flow or a public site, and the calendar size.
2. ShapeWhat each pick saves: one record per day, per range, per time block, one with breaks, or a booking of one resource or several.
3. Jump startThe saved object, with the link, date, title, status, times and resource fields filled in for you. Tabs for rules, closed days, views, hover card, status and every other setting.
4. ReviewEvery section with a Change link and a live preview, then save. The wizard shows the Config Name to paste.

The shape decides everything

The guided setup asks about the shape of the records you want, rather than about properties. Six cards, each with a small picture of what people pick and what lands in Salesforce:

  1. One record per day, or per range? Monday through Friday for six weeks can be thirty records or six.
  2. One record per time block, or one with breaks inside? A training day with a lunch break can be two records or one plus a break.
  3. Booking a room or person? One at a time, several at once, or add one to a range, a time block or a day with breaks.

You choose that here, on purpose, before any data exists. The shape also picks the right component, so there is nothing else to decide.

A live preview, before anything is saved

The preview on the Review step renders a working calendar from your choices. Turn on two-month view and it appears. Add status colors and the cells fill. It is the actual component, so what you approve is what you deploy.

The expensive mistakes in scheduling configuration are shape decisions you cannot see until real records exist. Seeing the calendar respond while you are still deciding removes most of that risk.

Inside the jump start: Fields, Times, Status

Two tabs do most of the heavy lifting on a booking or scheduling config. Times sets the hours people can book, the slot length, the gap after a booking and the notice, and maps the start and end time fields. Status is where the visual polish lives: a color for each status, the statuses to hide, and the ones people may pick.

On Status & Display, pick a status field, map a color to each value, and choose whether the color paints the calendar cell, the time slot grid, or both. Add hover fields so pointing at a booking previews the details.

What it actually writes

Saving deploys a Custom Metadata record. Three things follow:

  • It is deployable. Custom Metadata moves through your normal release pipeline, sandbox to production, like any other component.
  • It is reusable. Put the name in Config Name on any component and it picks up the whole configuration. One config, many placements.
  • It stays in your org. Nothing is stored on a vendor server, so the configuration is yours and it is visible in Setup.
About the deploy. Custom Metadata deploys are asynchronous. The wizard waits about two minutes and then, if the record has not appeared, shows you the deploy id and a link to Setup → Deployment Status. A busy org can take longer than the wizard waits, and the deploy still finishes.
Who can run it. Assign MultiDatePick - Setup to admins who build configs. It includes the Setup Wizard. Everyone who uses the calendars gets MultiDatePick - User, and MultiDatePick - All Access covers both.

Import, export, and the mapping step people miss

The Import tab takes a JSON configuration and turns it into a saved config. That is how the Config Library works: 40+ ready-made configurations covering time-off requests, room booking, hot-desking, interview scheduling, fleet reservation and more.

The step that saves the most time is Smart Field Mapping. Library configs reference the demo objects; your org has its own. The wizard scans every reference the moment you paste, flags each one your org does not have, and puts a dropdown next to it sourced live from the object's real field list. Remap in the wizard, click Apply, and it deploys with the rewritten JSON. No text editor, no hunt and replace, no re-uploads.

Export works the same way in reverse, which makes configurations shareable. A config that works in one org is a paste away from working in another.

Using the config once it exists

Drop any of the three components onto a Lightning record page, app page, Home page or Experience Cloud site, set Config Name to the name you chose, and leave every other property blank. The config supplies them. On App, Home and Experience pages, put the parent record in Static Parent Record Id.

The same applies inside a Screen Flow: put the config's name in Config Name and every on/off setting comes from the config. You do not set a single checkbox in Flow Builder; the few flow-only ones (Required, Show Inline, Output Date Ranges as JSON) are off unless you turn them on. Pass the parent record into Parent Record Id.
