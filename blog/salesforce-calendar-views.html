Five Calendar Views, One Salesforce Component

A month grid is the wrong shape for half the scheduling questions people actually ask. Here is why we added four more views, and how choosing between them became a config field instead of a rebuild.

Published August 21, 2026 · Updated October 21, 2026 · MultiDatePick

Every calendar starts as a month grid, because that is what the word makes you picture. Then people start asking questions it cannot answer. "Who is free Thursday afternoon?" "Is Room 4 booked solid next week?" "Which technician is over capacity?" The grid holds all of that data. It just makes you hunt for it.

MultiDatePick now renders the same records five ways. One component, one set of field mappings, one save path, and a View setting that changes the layout.

The five views, and the question each one answers

Each view is built for one question. Same records underneath, drawn the way that question needs.

Calendar

What is happening on the 14th?

A month at a time, each day filled with the status of what is booked on it. Days that mix statuses get diagonal stripes. The default, and still the right answer most of the time.

Interactive
Timeline

Which resource is free, and when?

Resources down the side, dates across the top. A booking that spans three days draws as one bar, overlapping bookings stack into lanes, and a capacity strip shows how full each day is. Zoom from a single day to a whole month, and drag a bar to move or stretch it. More on the Timeline view.

Interactive
Week

Who is free Thursday at 2pm?

Seven days across, business hours down, each booking sized to its real length. Bookings that overlap sit side by side in their own status colors, and the strip beside them stays open so you can add one more.

Interactive
Utilization

Who is over capacity?

Booked against capacity, per resource per day, on one blue scale. Overbooked days get an orange ring, and a combined row sums the team. Click any cell to drop into that resource's week. More on the utilization heatmap.

Read only
Agenda

What is next?

A flat list of the next 60 days, grouped by date, with the times, statuses and fields you pick. Reads well on a phone and in a shift handover.

Read only

Utilization and Agenda are read only by design: they answer a question rather than take a booking. The other three are fully interactive.

Five views, one definition of a booking

The usual version of this story ends with a second component: its own fields, its own save logic, its own bugs. Here all five views read the same records through the same field mappings, honor the same conflict rules and blocked dates, and write through the same save path. Switching from Calendar to Timeline cannot change what a booking means, because there is only one definition of a booking.

Two settings control it:

View

Which layout the component opens on: Calendar, Timeline, Week, Utilization or Agenda.

Available Views

The views the switcher offers. Leave it blank to offer all five, or narrow it to the two that make sense for this page.

So one component becomes three different tools. A recruiter's Interview Scheduling page opens on Week, because interviews are a time-of-day problem. A facilities manager's Room Booking page opens on Calendar with Timeline and Utilization alongside, because rooms are a capacity problem. A wall display opens on Agenda and offers nothing writable at all.

The default view is always in the switcher, whether or not you list it in Available Views. That list only needs the extras, which removes a whole class of "I restricted the views and now my own default is gone" confusion.

Choose the view per placement

An org-wide calendar setting is close to useless, because one company is not asking one question. Sales wants next week. Operations wants next quarter. A shift manager wants today, by the hour. Finance wants a utilization number.

View is set on each placement of the component. Put MultiDatePick on four record pages, a Flow screen, a Home page and a public Experience Cloud site, and each can be a different view of the same objects. No second install, no field mappings to keep in sync.

Timeline has two settings of its own:

SettingWhat it doesAPI name
Timeline Window (Days) How many days are on screen at once. Defaults to 14. A full month of columns leaves each booking about twenty pixels wide and clips every label, so the window exists to keep the view readable. Set it to 0 if you want the whole month. timelineWindowDays
Max View Resources How many resource rows to draw, busiest first. Keeps a list of eighty rooms from turning the view into a wall. maxViewResources

When one resource has several overlapping bookings, its row collapses to a single strip with a count, and expands on click into one lane per booking. Density becomes something the user chooses rather than something the data inflicts on them.

Point the resource lookup at User and it becomes people scheduling

The resource lookup points at any object. Rooms gives you room booking. Equipment gives you checkout. Point it at User and every view above becomes a staffing tool: Timeline is a roster, Week is a shift grid, Utilization is a team capacity dashboard. Managers ask "who is over capacity" about people far more often than about rooms.

Two practical notes if you try this. User has no standard capacity field, so add a custom one if you want Utilization to show percentages rather than raw counts. And if you point Business Hours Start Field and Business Hours End Field at fields on User, the Week grid honors each person's own working hours instead of one org-wide range.

There are two ready-made configs for exactly this in the library: Team Capacity Planning, which opens on the Utilization heatmap, and Staff Shift Roster, which opens on Timeline. Both use User as the resource.

Every config in the library now ships with a view already chosen

Picking a default view is a judgment call, and it is easier to copy one than to make one. So every config in the Config Library now specifies both a default view and a switcher list, chosen for what each config is actually for:

Interview and appointment configsWeekopen on the hours of the day
Room, desk, fleet and lab configsTimelineUtilizationwho has what, and how full
PTO, blackout and other date rangesTimelinea multi-day record draws as one bar
Date-only configsCalendarAgendaAgenda as the read-only companion
Anything with a capacity fieldUtilizationpercentages of capacity
The default is always a writable view. A read-only default would hide the config's main job, so Utilization and Agenda are only ever offered alongside.

Import any of them, remap the field names to your own schema, and the view choice comes along with it.
