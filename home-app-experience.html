App Pages, Home Pages & Experience Sites

MultiDatePick works on every Lightning surface, not just record pages. The trick is one property: Static Parent Record Id.

Watch the Setup Troubleshooting

Why these surfaces are different

MultiDatePick saves the dates you pick as records on a related object, each one linked back to a parent record. The component just needs to know which parent.

  • On a record page (e.g. an Event record), Salesforce automatically hands the component the current record's Id (the recordId). Nothing extra to configure.
  • On an App Page, Home Page, or Experience Site, there is no "current record." Salesforce passes nothing. With no parent, the component has nowhere to save, so it hides the Save button by design rather than show one that fails on click.
The fix is the Static Parent Record Id property. Paste a specific parent record's Id into it, and the component behaves exactly as if it were sitting on that record's page. It is a property you set in the builder. It has nothing to do with a Salesforce Static Resource, which is a separate feature for uploaded files.

Find Static Parent Record Id in the property panel after you drag MultiDatePick onto an App Page or Home Page in Lightning App Builder, or onto a page in Experience Builder.

Static Parent Record Id vs. a Flow: when to use which

Static Parent Record Id points the component at one fixed parent, so every visitor sees the same record. That is perfect for some cases and wrong for others. When the record needs to change per user or per visit, drive it from a Screen Flow instead. Drop the component on a Flow screen and bind its Parent Record Id to a variable the Flow resolves at runtime.

Use Static Parent Record Id when the record is the same for everybody

  • A public booking page: a guest-facing "request an appointment" page where every booking attaches to the same parent record (one office, location, or resource). A fixed Id is exactly right.
  • One org-wide calendar: a single "Company Closures" record, or one shared resource everyone books, that never changes per user.
  • A fixed dashboard anchor on an App or Home page that always points at the same master record.

Rule of thumb: reach for Static Parent Record Id when the answer to "whose record is this?" is "the same one for everybody."

Use a Flow when the record is chosen at runtime

  • Per-user records: each person sees only their own (for example, every contractor lands on their own PTO calendar). The Flow does a Get Records where the owner or a linked Contact = {!$User.Id}, stores the Id, and passes it to the component.
  • URL-driven: a Flow input variable reads ?id=… from the link, so one page serves many records. This works for guests too, with no login.
  • Pick-first: screen 1 lets the user search or choose (an employee, a room, a client); screen 2 shows that record's calendar.
Guest sites: on a no-login public site the "user" is a single shared guest, so per-user ($User) resolution does not apply. Either share one record through Static Parent Record Id, or drive it from a URL parameter through a Flow. True per-user calendars need logged-in users.

Public guest sites: the five-step checklist

A public Experience Cloud page lets anyone book without logging in. Do all five before you test as a guest. Steps 4 and 5 are the two most often missed. See it working on the live demo, a public guest site.

#StepWhat to set
1Object permissionsGive the site guest user Read, and Create if guests submit, on each object the component uses. Guests can never Edit or Delete. That is a Salesforce guest license rule for every app, so keep edit and cancel on pages behind a login.
2Field-level securityRead on every field the calendar shows. Edit on every field it writes, including status, time and relationship fields. Include the resource business hours and closure fields too.
3Guest sharing ruleA Read sharing rule for the guest user, so guests can see the records. The object's external org-wide default must be Private for the rule to apply. A rule deployed as metadata needs one click on Recalculate in Sharing Settings.
4Guest permission setAssign MultiDatePick - Guest to the site's guest user. It carries the Apex class access the calendar loads its data through, plus the read and create rights a guest may have on the MultiDatePick objects.
5Publish and activatePublishing and activating are separate steps. Guests only see an activated site.

Two org settings guests also need

SettingWhy
Default record ownerGuests cannot own records, so Salesforce assigns every guest booking to a default owner. Set it in Experience Workspaces, Administration, Preferences.
Read access to referenced recordsA booking that points at a resource or parent needs guest Read on that record, or the save fails with a cross-reference error. Use a custom object for anything guests book against: guest access to Contacts and Accounts is heavily restricted.

Troubleshooting

SymptomFix
Save never appearsOne of the four is empty. Off a record page it is usually Static Parent Record Id.
Calendar loads, saving failsNo object access. Assign the MultiDatePick - User permission set; on a site, give the member or guest profile read and create.
"Field does not exist" on saveAPI name typo. Copy it from Setup, Object Manager. A namespace prefix is only for another package's objects (e.g. acme__Visit_Date__c).
Site members can't see their recordsAdd a sharing rule (or loosen org-wide defaults) on the child object.
Saved dates vanish on refreshKeep Load Existing Dates on (it is on by default).
Static Parent Record Id "isn't valid"Use a real 15 or 18 character Id of the parent object, the one the Relationship Field points to.
